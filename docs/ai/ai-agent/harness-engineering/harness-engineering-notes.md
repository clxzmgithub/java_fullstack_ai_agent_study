# Harness Engineering 学习笔记

> 知识来源：JavaGuide AI Agent 系列文章学习整理
> 关联文档：`harness-engineering.md`、`agent-basis.md`

---

## 一、核心公式：Agent = Model + Harness

```
Agent = Model + Harness
模型负责推理和生成
Harness 负责把模型放进一个可执行、可观察、可恢复、可验证的工作环境里
```

**类比**：模型是 CPU，Harness 是操作系统。CPU 再强，OS 如果天天崩，体验也不会好。

---

## 二、为什么瓶颈经常不在模型？

> 一个典型实验：同一个模型，只换了文件编辑接口的调用方式，编码基准分数从 **6.7% 跳到了 68.3%**。

**结论**：决定 Agent 表现上限的，往往不是模型，而是模型外面的工程环境。

- 工具接口设计得很难用 → 模型再强也被外部环境拖住
- 反馈回路缺失 → 错误信息不给修复方向，模型无法自我纠正
- 上下文管理不当 → 噪声越来越多，推理质量下降

## 三、四个核心属性详解

### ✅ 可执行（Executable）

> **模型会"说"，Harness 让它能"做"**

模型只能输出文字或结构化调用指令，它没有手，无法真正运行代码、操作文件或调用 API。Harness 提供：

- **代码执行环境**（Bash、沙箱）：模型说"跑这段 Python"，Harness 真的跑起来
- **文件系统操作**：读文件、写文件、Git 提交
- **工具调用链路**：MCP Server、Function Calling，把模型的意图变成真实的系统动作

> 没有可执行环境，Agent 只能停留在"给建议"阶段。

---

### 👁️ 可观察（Observable）

> **知道 Agent 在做什么、做到哪一步了**

Harness 提供：

- **链路追踪**（Trace）：记录每一步推理 → 工具调用 → 结果回传
- **日志和指标**：比如 Carlini 的编译器项目里"日志全写进文件、用 `grep` 友好的单行格式"
- **上下文利用率监控**：监控是否接近"40% 阈值"，提前预警
- **可视化**：OpenAI 把 Chrome DevTools Protocol 接进 Agent，让 Agent 自己也能截图、看 DOM

> 可观察性把"Agent 感觉跑得不好"变成"具体哪个节点出了问题"这种可测量、可排查的问题。

---

### 🔄 可恢复（Recoverable）

> **出了错，能回来；跑太久，能重启**

Harness 提供：

- **重试 / 回滚机制**（对应六层架构的 L6：约束、校验与恢复层）
- **Context Resets**：Anthropic 的做法是上下文快满时"结构化提取当前状态 → 启动干净 Agent → 从检查点继续"
  - 类比：程序内存泄漏时重启进程再从 checkpoint 恢复
- **进度文件**：用 JSON 记录任务状态，Agent 重启后知道从哪里接着干
- **最大迭代轮次兜底**：防止死循环，设置上限强制退出（一般 10~20 轮）

> 没有可恢复性，一个长任务失败就意味着从头开始，代价极高。

---

### ✔️ 可验证（Verifiable）

> **Agent 能知道自己有没有做对，而不是自己夸自己**

Harness 提供独立于生成过程的验证机制：

- **沙箱 + 测试**：Agent 写完代码，真的跑测试，看测试是否通过
- **浏览器自动化验证**：Anthropic 的 Evaluator Agent 用 Playwright 实际点击运行中的应用
- **自定义 Linter + 修复指令**：工具不只是报错，还告诉 Agent 具体怎么改
- **架构结构测试**：OpenAI 的原则——"If it cannot be enforced mechanically, agents will deviate"

> 关键：验证必须是**独立视角**。让 AI 生成测试再用这些测试验证 AI 生成的代码，就像"用同一双眼睛检查自己的作业"，不够可信。

---

### 四个维度对应四类失控风险

| 属性   | 解决的问题              | 没有它会怎样                     |
|--------|-------------------------|----------------------------------|
| 可执行 | 模型只能说，无法做      | Agent 永远停留在"给建议"阶段     |
| 可观察 | 不知道 Agent 在做什么   | 出了问题无法定位，只能瞎猜       |
| 可恢复 | 长任务失败、上下文崩溃  | 任何错误都意味着从头开始         |
| 可验证 | 模型自我评价不可信      | Agent 自信地做错事，你却不知道   |

## 四、Harness 六层架构

> 把它想成给一个新员工搭工作环境：L1 是岗位说明，L2 是办公工具，L3 是标准操作流程，L4 是项目管理系统和笔记本，L5 是质检流程，L6 是红线规则和应急预案。

| 层级 | 名称               | 解决什么问题                   | 关键设计                                                    |
|------|--------------------|--------------------------------|-------------------------------------------------------------|
| L1   | 信息边界层         | Agent 该知道什么、不该知道什么 | 定义角色与目标，裁剪无关信息，结构化组织任务状态            |
| L2   | 工具系统层         | Agent 怎么和外部世界交互       | 选择工具、控制调用时机、提炼工具结果并反馈                  |
| L3   | 执行编排层         | 多步骤任务怎么串起来           | 让模型按"理解目标、判断信息、分析、生成、检查"的轨道推进    |
| L4   | 记忆与状态层       | 长任务中间结果怎么管理         | 独立管理当前任务状态、中间产物和长期记忆，避免状态混在一起  |
| L5   | 评估与观测层       | Agent 怎么知道自己做对了没有   | 建立独立于生成过程的验证机制                                |
| L6   | 约束、校验与恢复层 | 出错了怎么办                   | 预设规则拦截错误，失败时提供重试、回滚或降级                |

---

## 五、结合真实场景理解六层架构

**场景：让 Agent 排查 order-service 今天早上 9:00-9:30 为什么变慢**

```
用户："order-service 为什么变慢？"
         ↓
L1 信息边界层    → AGENTS.md 定义职责和权限边界：
                  "你是 SRE 值班 Agent，只能访问 order-service、user-service 数据"
         ↓
L2 工具系统层    → MCP Server 提供：
                   Resources（服务拓扑、DB Schema）← 给模型"看"
                   Tools（查慢SQL、查CPU、发报告）← 给模型"用"
                   Prompts（排查流程模板）← 给模型"遵守"
         ↓
L3 执行编排层    → 按"查CPU → 查慢SQL → 查错误日志"顺序推进
         ↓
L4 记忆与状态层  → 保存中间结论，支持断点续查（context reset 后新 Agent 继续）
         ↓
L5 评估与观测层  → 验证：慢SQL时间窗口是否与服务变慢时间段吻合？
         ↓
L6 约束校验恢复层 → 拦截越权操作（禁止写操作）；超时重试；触发上限保护
         ↓
输出："根因是 orders 表全表扫描，建议加索引 status 字段"
```

## 六、上下文的 40% 阈值现象

> Dex Horthy 的观察：168K token 的上下文窗口，用到大约 **40%** 的时候，Agent 输出质量就开始明显下降。

| 区间       | 占比      | 表现                                     |
|------------|-----------|------------------------------------------|
| Smart Zone | 0 ~ 40%  | 推理聚焦、工具调用准确、代码质量高        |
| Dumb Zone  | 超过 ~40% | 幻觉增多、兜圈子、格式混乱、代码变差     |

**Anthropic 的解法——Context Resets**：
- 上下文快满时，结构化提取当前状态
- 启动干净 Agent，把交接文档给它
- 新 Agent 从干净状态继续做

> 目标不是给 Agent 塞更多信息，而是让它尽量停留在干净、相关的上下文里。

## 七、Harness 成熟度阶段

| 阶段                  | 特征                                  | 工程师角色              |
|-----------------------|---------------------------------------|-------------------------|
| Level 0：无 Harness   | 直接给 Agent Prompt，没有结构化约束   | 手动写代码，偶尔使用 AI |
| Level 1：基础约束     | `AGENTS.md`、基础 Linter、手动测试    | 主要写代码，AI 辅助     |
| Level 2：反馈回路     | CI/CD 集成、自动化测试、进度追踪      | 规划和审查为主          |
| Level 3：专业化 Agent | 多 Agent 分工、分层上下文、持久化记忆 | 设计环境和管理执行过程  |
| Level 4：自治循环     | 无人值守并行化、自动清理、自修复      | 架构设计和质量把关      |

## 八、从哪里开始搭 Harness（优先级指南）

### P0：可以马上做
| 行动                        | 为什么                                           |
|-----------------------------|--------------------------------------------------|
| 创建 `AGENTS.md` 并持续维护 | Agent 每次启动自动加载，犯错后更新，形成反馈循环 |
| 写自定义 Linter + 修复指令  | 错误消息直接告诉 Agent 怎么改                    |
| 把团队知识放进仓库          | Slack、Wiki 里的知识对 Agent 很难稳定可见        |

> ⚠️ 坑：不要把 `AGENTS.md` 写成超级 System Prompt。OpenAI 的做法是约 100 行，详细规则放到子文档里按需加载。

### P1：P0 稳了之后补
- 分层管理上下文（渐进式披露）
- 建立进度文件和功能列表（JSON 追踪状态）
- 给 Agent 端到端验证能力（Playwright / Puppeteer）
- 控制上下文利用率（不超过 40%）

### P2：有余力再考虑
- Agent 专业化分工
- 定期垃圾回收（清理熵积累）
- 可观测性集成

## 九、核心认知总结

1. **瓶颈不总在模型**：同一个模型，换工具接口，分数能差 10 倍
2. **可执行、可观察、可恢复、可验证**是 Harness 的四个核心属性
3. **六层架构**：从边界、工具、流程、状态、验证到恢复，形成完整体系
4. **上下文 40% 阈值**：塞得越满不等于越聪明，越满往往越蠢
5. **验证要独立**：不能让模型自己验证自己的输出
6. **Harness 要定期简化**：模型变强后，旧的保护机制可能变成冗余
