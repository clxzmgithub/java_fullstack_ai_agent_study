# AI Agent 核心概念辨析：Function Calling / Tools / MCP / Skills / Host

> 知识来源：JavaGuide AI Agent 系列文章学习整理

## 一、概念总览

这几个词经常一起出现，但不在同一层，是嵌套关系，不是竞争关系。

```
┌─────────────────────────────────────────────────┐
│                  Host（AI 应用）                  │
│   Claude Desktop / Cursor / 自研 Agent 平台      │
│                                                 │
│  ┌──────────────┐   ┌──────────────────────┐   │
│  │   大模型推理  │   │     MCP Client       │   │
│  │              │   │   负责和Server通信    │   │
│  │ Function     │   └──────────┬───────────┘   │
│  │ Calling 输出 │              │ JSON-RPC       │
│  └──────┬───────┘              ▼               │
│         │               MCP Server             │
│         │          ┌────────────────────┐      │
│         └─────────►│ Tools / Resources  │      │
│                    │ Prompts（三类原语）│      │
│                    └────────────────────┘      │
│                                                 │
│  Skills（SKILL.md，按需注入上下文）             │
└─────────────────────────────────────────────────┘
```

## 二、逐个概念拆解

### 1. Function Calling —— 模型表达"我想调工具"的方式

**是什么**：模型识别出需要调外部工具时，输出的一段**结构化 JSON**。

**它只是模型的一个输出格式**，表达了意图，但本身不执行任何东西。

```json
{
  "name": "get_weather",
  "arguments": { "city": "北京" }
}
```

- OpenAI 叫 **Function Calling**
- Anthropic 叫 **Tool Use**
- 名字不同，干的是同一件事

> **关键**：模型输出这段 JSON 之后，什么都没发生。它只是说"我想做什么"，真正怎么执行完全不归 Function Calling 管。

---

### 2. Tools —— Agent 可以调用的外部能力集合

**是什么**：一个**泛概念**，指"Agent 能用的外部能力"。

可以是：
- 一个本地函数（`query_slow_sql`）
- 一个 HTTP 接口
- 通过 MCP 暴露出来的能力
- 一段 Python 脚本

Tools 关注"有哪些工具可以用"，不关心工具怎么接入进来的。

> Tools 是能力的**集合概念**，MCP 的 Tools 原语是 Tools 的一种**具体实现形式**。

---

### 3. MCP —— 工具接入的标准通信协议

**是什么**：解决"工具从哪来、怎么被发现、怎么被调用"的通信规范。

**解决的痛点**：没有 MCP 时，在 Cursor 里写一套工具接入逻辑，换到 Claude Desktop 又要重写，换到自研平台还要再写一套。MCP 定了统一标准，工具只需封成 MCP Server，任何支持 MCP 的应用都能用。

**三类原语**（Server 对外暴露的能力分类）：
- **Tools**：可执行动作（有副作用，模型主动调用）
- **Resources**：只读数据（给模型看的背景信息）
- **Prompts**：可复用提示词模板（固定任务模板）

---

### 4. Skills —— 任务经验的"操作手册"

**是什么**：一份可被 Agent 按需加载的**任务说明**，核心是 `SKILL.md` 文件。

把某类任务的经验、约束、执行顺序沉淀下来：
- 代码 Review 时先看架构还是先看异常处理
- 排查慢 SQL 的标准步骤是什么
- 输出报告时用什么格式

**Skills 不是 MCP 的替代品**，它更像**上下文注入机制**：Agent 读了一份说明书，然后把里面的规则纳入后续推理。

---

### 5. Host —— 承载用户交互的 AI 应用本体

**是什么**：用户直接面对的 AI 应用。

常见 Host：
- Claude Desktop（桌面 AI 助手）
- Cursor（AI 代码编辑器）
- VS Code + Copilot 插件
- 你自己做的 Agent 平台

Host 的职责：
1. 接收用户输入
2. 组装上下文（工具列表 + Skills 元数据 + 系统提示词）
3. 调用大模型推理
4. 连接 MCP Server（通过内部的 MCP Client）
5. 加载 Skills（根据大模型判断结果）
6. 展示最终结果

---

## 三、三者关系的完整调用链

```
用户："帮我查北京天气"
        ↓
Host 组装请求：
  [系统提示词] + [可用工具列表（来自 MCP Server）] + [用户消息]
        ↓
大模型推理，用 Function Calling 输出意图：
  {"name": "get_weather", "arguments": {"city": "北京"}}
        ↓
Host 里的 MCP Client 按协议请求 MCP Server
        ↓
MCP Server 里的 Tools（get_weather 函数）真正执行
        ↓
结果返回给大模型，大模型组织自然语言回答
        ↓
用户看到结果
```

**一句话类比**：
- Function Calling = 模型的**嘴**（表达意图）
- MCP = **快递系统**（把意图送到对的地方）
- Tools = 真正**干活的人**（执行能力本身）

## 四、模型怎么知道有哪些工具可以调？

这是理解整个体系的关键问题。

### 工具发现机制

**答案：Host 在每次发给模型的请求里，把可用工具列表一起塞进去。**

模型本身不会"记住工具"，它不会主动去查有哪些工具。每次请求时，Host 都会把工具描述作为上下文的一部分传给模型：

```
[系统提示词]
你是一个 SRE Agent，负责排查线上问题。

[可用工具列表]
工具1: get_cpu_metrics
  描述: 查询指定服务在某时间段的 CPU 使用率
  参数: service_name(string), time_range(string)

工具2: query_slow_sql
  描述: 查询慢 SQL 日志，服务响应慢、DB 超时时使用
  参数: service_name(string), time_range(string), threshold_ms(int)

[用户消息]
帮我排查 order-service 今天早上 9 点到 9 点半为什么变慢了
```

模型读到工具列表，才能做出"我要调 get_cpu_metrics"的判断。

### 工具列表从哪来？

```
MCP Server 启动
    ↓
MCP Client 连上去，发初始化握手："你有哪些工具？"
    ↓
MCP Server 返回：工具列表（名称 + 描述 + 参数 Schema）
    ↓
Host 收到工具列表，在每次调用模型时把它拼进请求上下文
    ↓
模型读到工具列表，推理时决定调哪个
```

> **工具发现（Tool Discovery）** 在正式对话开始前就完成了，是一个初始化阶段的握手过程。

## 五、MCP Prompts 原语 vs Agent Skills 的区别

这两者都是"任务说明"，容易混淆，但有本质区别：

| 维度         | MCP Prompts 原语                  | Agent Skills（SKILL.md）            |
|--------------|-----------------------------------|-------------------------------------|
| **存放位置** | MCP Server 里                     | 项目代码仓库（`.claude/skills/`）   |
| **内容**     | 单个任务的提示词模板              | 完整任务的做法、约束、流程、脚本    |
| **加载方式** | Host/用户界面触发（按钮/命令）    | 大模型判断命中后，Host 执行加载     |
| **适合场景** | "生成故障复盘初稿"这类固定模板    | "代码 Review 规范"这类团队经验沉淀  |
| **触发机制** | 外部触发（人或程序）              | 模型推理 + Host 执行（两步配合）    |

## 六、Skills 的加载机制详解

**"Agent 自己判断任务是否命中"这个说法不精确。**

准确说法：**大模型推理判断，Host 执行加载，两者配合完成。**

### 完整流程

```
第1步：Host 启动时扫描 .claude/skills/ 目录
       只读取每个 SKILL.md 的元数据（名称 + 一句描述，很短）
       把所有 Skill 元数据列表放进上下文

第2步：用户说"帮我做 TDD 开发"
       Host 把 [用户消息 + Skill 元数据列表] 一起发给大模型

第3步：大模型读到元数据列表，推理出：
       "test-driven-development 这个 Skill 命中了"

第4步：Host 收到这个判断，去读 SKILL.md 完整内容
       把完整内容注入上下文，再重新发给大模型

第5步：大模型读到完整 Skill 内容，按里面的规矩执行任务
```

### 为什么要分两步（延迟加载）？

**上下文 Token 是有限的，不能一开始就把所有 Skill 的完整内容全塞进去。**

- 假设有 20 个 Skill，每个 500 字 → 全塞进去 = 10000 字，大量 Token 浪费，且大部分 Skill 跟当前任务无关
- 延迟加载：启动时只放 20 行元数据 → 模型判断命中 1 个 → Host 只加载这 1 个完整内容

> 这正是 L1 信息边界层的核心原则：**在正确的时机，给模型正确的信息，裁掉无关内容**。

## 七、Skills 和 Harness 六层架构的关系

Skills 不是六层架构中的某一层，而是**横跨多层的工程实践机制**。

| 架构层          | Skills 的影响                                        |
|-----------------|------------------------------------------------------|
| **L1 信息边界层** | ★ 主要落脚点：把任务规矩注入上下文，渐进式披露         |
| **L2 工具系统层** | Skills 里可声明要调哪些工具，驱动工具调用              |
| **L3 执行编排层** | Skills 里的 Flow 给 Agent 提供推进轨道                |
| **L5 评估层**    | Skills 里可写 Done Checklist（验收标准）              |
| **L6 约束层**    | Skills 里可写禁止事项（Ask Before Skipping）          |

## 八、全部概念汇总对照表

| 概念              | 是什么                         | 解决什么问题                       | 类比                   |
|-------------------|--------------------------------|------------------------------------|------------------------|
| **Function Calling** | 模型输出结构化调用意图的格式  | 模型怎么"说"它想做什么             | 你写了一张工单         |
| **Tools（泛）**   | Agent 可用的外部能力集合       | 有哪些能力可以用                   | 工具箱里的工具         |
| **MCP（协议）**   | 工具接入的通信规范             | 工具怎么被标准化发现和调用         | 快递系统的规范         |
| **MCP Server**    | 实现了 MCP 的服务程序          | 把具体能力封装并暴露出去           | 干活的部门             |
| **MCP Client**    | Host 里负责和 Server 通信的模块 | 发工单的人                        | 需求对接人             |
| **Tools（原语）** | MCP Server 暴露的可执行动作    | 能做什么事（有副作用）             | 研发能提供的功能接口   |
| **Resources（原语）** | MCP Server 暴露的只读数据  | 能看什么数据（无副作用）           | 研发开放的只读接口     |
| **Prompts（原语）** | MCP Server 暴露的提示词模板  | 固定任务怎么做                     | 标准操作手册           |
| **Skills**        | 可按需加载的任务说明（SKILL.md）| 把团队经验/任务流程固化给 Agent    | 老员工脑子里的规矩     |
| **Host**          | 承载用户交互的 AI 应用本体     | 用户和 AI 能力之间的集成层         | 用浏览器上网的人       |
| **原语（Primitive）** | 不可再分割的最小功能单元    | 定义系统对外能力的基础分类         | 操作系统的系统调用类别 |

## 九、核心认知总结

1. **Function Calling 只是模型的输出格式**，不负责执行，只负责表达意图
2. **MCP 解决接入标准化**，工具团队封 Server，AI 应用连 Client，两边解耦
3. **三类原语的核心区别**：Tools 有副作用主动调、Resources 只读被动提供、Prompts 是模板
4. **Skills 是上下文注入机制**，不是工具，是"任务说明书"，横跨 Harness 多层
5. **Host 是整合者**：组装上下文 + 连 MCP + 加载 Skills + 调模型 + 展示结果
6. **模型不会"记住"工具**：每次都由 Host 把工具列表塞进请求上下文，模型才知道有哪些工具
7. **Skills 加载是两步走**：大模型推理判断命中哪个 Skill，Host 执行加载完整内容
